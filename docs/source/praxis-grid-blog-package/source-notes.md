# Research notes and editorial verification

**Research date:** November 17, 2026 (America/Kentucky/Louisville)
**Scope:** Public GitHub sources at **pinned** default-branch revisions; primary sources include implementation files, config API documentation, sample deployments, and automated test harnesses. No private tree, local patch, or unpublished demo was used.
**Method:** Read repository contents and source through GitHub access, and cross-check relevant upstream project documentation. This is a source review, **not** a runtime certification. No `cargo` tests, Kubernetes clusters, inference requests, or performance benchmarks were executed for this blog package.

## Source-to-claim index

### Praxis: mechanics and backend status

- [Architecture and filter-first request processing](https://github.com/praxis-proxy/praxis/blob/2212314b12a4536774f41ed4e1aec1619d403459/docs/architecture/overview.md) and [request lifecycle](https://github.com/praxis-proxy/praxis/blob/2212314b12a4536774f41ed4e1aec1619d403459/docs/architecture/life-of-a-request.md): listeners, chains, middleware hooks, reload behavior, backend-neutral abstractions.
- [Hyper backend implementation guide](https://github.com/praxis-proxy/praxis/blob/2212314b12a4536774f41ed4e1aec1619d403459/docs/architecture/hyper-backend.md), [backend feature declarations](https://github.com/praxis-proxy/praxis/blob/2212314b12a4536774f41ed4e1aec1619d403459/crates/server/Cargo.toml), [protocol implementations](https://github.com/praxis-proxy/praxis/tree/2212314b12a4536774f41ed4e1aec1619d403459/crates/protocol/src/http): **Pingora default**, **Hyper opt-in**, exclusive build features and known non-parity. Hyper supports many request/filter paths but is **not** a drop-in claim of full HTTP feature parity.
- [Root workspace manifest](https://github.com/praxis-proxy/praxis/blob/2212314b12a4536774f41ed4e1aec1619d403459/Cargo.toml) identifies Pingora crate dependencies with a comment referencing the [Praxis Pingora fork](https://github.com/praxis-proxy/pingora). Pingora upstream and Praxis's adapters/fork are distinct projects.
- [Upstream Envoy dynamic configuration documentation](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/dynamic_configuration) was used for a balanced architectural comparison, not a benchmark.

### AI: model, state, authorization and token controls

- [Intelligent route filter](https://github.com/praxis-proxy/ai/blob/3c08a9a63b80d128693732166169d01dc820199c/docs/filters/intelligent_route.md) and [implementation](https://github.com/praxis-proxy/ai/blob/3c08a9a63b80d128693732166169d01dc820199c/filters/src/routing/intelligent_route.rs): matched capability, admitted candidates, selection groups, deterministic/round-robin/random/weighted modes, snapshot validation and session reuse. Not equivalent to Grid gateway `grid_site_route`.
- [Agentic protocol architecture](https://github.com/praxis-proxy/ai/blob/3c08a9a63b80d128693732166169d01dc820199c/docs/architecture/agentic-protocols.md): JSON-RPC metadata, MCP broker and A2A task routing; the documented A2A local task map is in-process with TTL, not a promised global distributed state store.
- [Response store](https://github.com/praxis-proxy/ai/blob/3c08a9a63b80d128693732166169d01dc820199c/docs/architecture/response-store.md), [Responses configs](https://github.com/praxis-proxy/ai/tree/3c08a9a63b80d128693732166169d01dc820199c/examples/configs/openai/responses), and [store-backed tests](https://github.com/praxis-proxy/ai/tree/3c08a9a63b80d128693732166169d01dc820199c/tests): stateful requests are a first-class path; configuration and storage mode govern durability and ownership.
- [Token rate limiting](https://github.com/praxis-proxy/ai/blob/3c08a9a63b80d128693732166169d01dc820199c/docs/filters/token_rate_limit.md): **feature-gated**; reserves estimates, reconciles after completion, supports a shared backend, and has explicit backend failure and metering contracts. No claim that this automatically keys the budget by authenticated user across every Grid deployment.

### Grid: operator, routing, metrics, trust and test proof

- [Architecture](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/overview.md) and [overlay implementation architecture](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/routing.md): the operator reconciles and renders; Praxis handles inference traffic from accepted local state; global DNS/Anycast ingress is a separate component.
- [Routing policy and groups](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/routing.md) and [provider scoring](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/scoring.md): `geographyFirst` vs `scoreFirst`, group selection vs picker, default `noMetrics`, and **single** named public scoring strategy. The lower-level [scoring crate](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/scoring/src/scoring.rs) has general weighted scoring utilities; it is **not** the published `GridNetwork` `scoringPolicy` schema.
- [Operator metrics parser](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/operator/src/metrics_parser.rs), [provider metric collection](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/operator/src/resources/provider_metrics.rs), and [site signal adapter](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/gateway/crates/ai-grid-filters/src/signals/llm_d.rs): Prometheus text parsing, configurable mapping, ready endpoints, running/queued counts, held work, KV-cache mean/spread, freshness and derived pressure. These signals are not evidence of GPU throughput.
- [Grid site selection](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/site-selection.md) and [request-time site routing implementation](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/gateway/crates/ai-grid-filters/src/route.rs): separate Grid-serving path using locally accepted readings, pressure tiers, optional shedding and local affinity.
- [Prefix affinity and owner tags](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/prefix-affinity.md) and [site route candidate admission checks](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/gateway/crates/ai-grid-filters/src/route.rs#L1094-L1136): existing state is pinned by owner, but the reviewed code checks new-work admission in the pinned path. Do **not** promise a continuation always succeeds during `existing_only` drain.
- [Provider drain](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/provider-draining.md), [admission implementation](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/operator/src/resources/provider_admission.rs): administrative drain can set `existing_only`, subject to health and trust. It does not introduce a bounded drain deadline or state migration.
- [Signal transport](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/signals.md), [signed state](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/signed-gossip-trust.md), [auth and peer policy](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/architecture/auth.md): SWIM membership persists regardless of whether telemetry gossips or is polled; signed state is optional/off by default; site identity does not replace request-level authorization.
- [Technical preview scope](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/technical-preview-scope.md): external ingress, inter-cluster networking, model deployment, tenant auth, and remote Kubernetes config delivery remain deployment responsibilities.
- [Grid release guide](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/docs/release.md): the release qualification matrix distinguishes different release, opt-in, and demo qualification categories. It is a **test plan/description**, not evidence we executed that matrix on the reviewed SHA.
- [llm-d pool-metrics qualification fixture](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/tests/e2e/topologies/grid-llmd-pool-metrics/README.md), [xtask implementation](https://github.com/praxis-proxy/grid/blob/427fe3e602417623cf395ee223c224a8e5e95dcd/crates/xtask/src/env/llmd_pool_metrics_demo.rs): EPP + synthetic inference simulators, route switching/recovery and peer signal checks, **not** GPU performance measurements.

## Test-evidence hierarchy and exclusions

1. **Code and unit tests reviewed:** provide evidence that code paths and assertions exist; do not prove a running deployment at this revision.
2. **Controlled integration fixtures inspected:** Grid Kind/Forge test topologies for provider routing, llm-d metrics, cloud/global ingress and quota. The simulator-based llm-d experiment exercises metrics ingestion, transport, pressure changes, and selected routes—not real GPU scheduling behavior.
3. **Release qualification:** Grid's release file classifies test lanes and expected evidence; no claim made that this article ran them or checked a successful run for this SHA.
4. **Live GPU / enterprise rollout / performance:** not tested; no claims of latency percentiles, money saved, throughput, compliance certification, or replacement of an entire Envoy or networking stack.

## Material uncertainties to review before publication

- **Stored continuations while draining:** Current Grid-serving `route.rs` uses a new-work admission predicate in the pinned-target lookup; docs explicitly describe 503 for a non-admitting owner. A separate branch or future fix may change this. The article intentionally does not promise existing-only continuations; confirm against the exact intended release/feature path.
- **Tenant authorization in external ingress:** Grid's auth documentation states that site-level provider access is not a full request-time tenant/model policy. For public deployment, document an actual configured identity and authorization integration at both ingress and provider boundaries.
- **Two routing surfaces:** `intelligent_route` overlay semantics differ from Grid gateway `grid_site_route` signals and affinity semantics. Choose one actual deployment mode before copying examples or drawing performance conclusions.
- **Dynamo integration:** no reviewed native Grid adapter or test fixture. Treat as prospective until a metric mapping, implementation, qualification, and compatibility matrix are checked.
- **Quota and request-rate mechanisms:** AI's reservation-based limiter and Policy's soft Limitador quota are separate mechanisms; avoid implying universal exactness, idempotency, stream usage accuracy, or distributed tenant-key support.
- **Backend parity:** Hyper is opt-in and not feature-equivalent to Pingora. Upstream fork details and supported versions should be rechecked at release time.
- **External providers:** a model name is not a compatibility contract; translation, provider credentials, policy boundaries, and quotas must be verified for each overflow path.

**Excluded intentionally:** invented benchmark numbers; unverified “better than Envoy” performance claims; Dynamo integration presented as complete; every policy project capability attributed to Grid; SWIM presented as a synchronous scheduling service; full tenant isolation inferred from topology alone; and automatic state transfer during failover.
